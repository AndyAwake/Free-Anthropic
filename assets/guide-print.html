01｜第一眼：我从 Claude 迁过来，应该用哪个？

先按任务分流，不搞一张没有证据的「谁最强」排行榜。聊天/写作先用可用的轻量助手试一段真实需求；Claude Code 用户先将 Git 源码和工程约束搬出来，再用 Codex 或可用的执行工作台做一次可运行修改；Projects/知识库 用户先做清理后的交接卡；需要离线的团队先审查设备与本地模型许可。

按场景看完整平替矩阵 · Claude Code 迁移工程教程 · 能力移植方法论

本网站提供一个按任务推荐首轮试用路线的工具选择器，选择不需要登录或上传任何素材。推荐只是尝试顺序，不代表你所在地区、账号和套餐必然可用。

02｜先讲结论：选工作流，不是选一个聊天窗口

AI 替代失败通常不是“模型不会回答”，而是输出文件拿不走、真实模型看不清、费用失控、功能或地区不支持、换同事无法复现。你真正需要的是 输入 → 模型/工具 → 人工核验 → 可编辑成品 → 记录成本 → 下次可重跑。

今天不必同时注册十款工具。用一份公开材料做一项真实任务；只有它能满足交付标准，才考虑第二款工具或者自动化。把未知写成“未测”，不编造评分、价格和收益。

03｜先看六类常见任务

场景 小白首轮路线 必须留下的成品 一句话验收
公众号 / Threads 文章 国内可用助手 + 人工审校 Markdown / Word + 来源表 事实、语气、来源正确
学习和资料阅读 Kimi / 豆包等支持的入口 证据摘录表 + 摘要 能逐条找回原文
业务表格与分析 助手生成结构化数据 + Excel/WPS CSV / XLSX + 公式说明 换人能复算
网站 / 编码 WorkBuddy 或 Codex 等受支持工具 源码 + README + 截图 能打开、有发布步骤
产品演示视频 真实产品 UI 录制 + 分镜 + 剪辑 素材、分镜、成片、授权记录 所见功能真实存在

“建议先试”不是所有地区、所有套餐均可用的保证。具体产品支持情况、文件功能和费用，必须在使用时查官方页面与账号实际入口。

04｜工具选择的七个必要条件

采用 7 维比较表，而不是“我觉得它厉害”：

  1. 能否使用：地区、账号、行业合规与必要权限。
  2. 输入能力：能读取你实际有权使用的文字、表格、图片或代码吗？
  3. 输出可带走：成品是否可编辑、可下载，能否复用？
  4. 准确与一致：重要事实是否能溯源？每次格式是否稳定？
  5. 真正的成本：订阅、API、运行、人工修正、审核和托管。
  6. 模型透明度：工作台实际使用哪个模型，是否有回退或路由？
  7. 可恢复性：账号异常后，资料和工作能否继续？

一项工具哪怕第 4 项表现不错，如果第 1、3 或 7 项不过关，也不适合作为某类核心业务的唯一依赖。

05｜中国用户从哪里开始：不要混淆应用与 API

豆包、Kimi： 适合先在网页或客户端完成明确的小任务。登录后粘贴自己有权使用的材料，先让它复述资料清单，再生成结果，最后复制或下载为本地文件。具体界面功能以账号实际显示为准。豆包 · Kimi。

WorkBuddy： 工作台不等于固定模型。创建任务前记录选择器里的模型/模式；如果界面只显示 Auto 而没有真实后端记录，就标记“实际模型待核实”。指定有限的本地任务目录，避免让自动化接触不必要的文件。模型选择文档。

国内 API： 当任务已经标准化，才考虑火山方舟、Kimi 开放平台、阿里云百炼、DeepSeek 等对应官方 API。订阅、网页免费权益与 API 计费通常是不同产品，不要默认“开了会员 API 就免费”。

Gemini / OpenAI： 适合实际产品、账户和所在地区满足官方支持条件的用户，同题对照其文本、文档、编码等能力。不要在面向中国大陆读者的保姆级教程里暗示这些服务都可无条件直接使用，也不提供绕过地区限制的操作。

06｜把一项任务拆成六步

Step 1：写需求卡。 写出“输入是什么、给谁看、交付什么格式、什么情况算失败”。

Step 2：固定公开原料。 初次比较尽量用公开资料。涉及客户内容须授权，并在适当环境下处理。

Step 3：先让模型确认理解。 要求它列出已读取的文件、关键约束、缺项和可能风险，不要立即生成漂亮成品。

Step 4：生成第一版。 将结果保存到 output/v1；哪怕模型答得好，也不算已经落地到文件。

Step 5：人工验收。 检查事实、格式、可运行性、授权、品牌和移动端显示。

Step 6：保存复用模板。 留下原料、提示词、最终成品、耗时、费用与改稿记录。另一工具可使用同一套输入再跑。

07｜可直接复制的总提示词

你是一位按交付标准工作的协作者。
场景：[例如：把公开政策资料改写为读者友好的说明文]
读者：[普通用户/企业客户/工程师]
输入资料：[粘贴有权使用的资料；附来源与日期]
必须保留：[事实、链接、术语、技术限制]
不得出现：[编造结果、无法核实的数据、未授权信息]
产物：[例如 1 篇 Markdown + 1 张 CSV 证据表]
验收：
1. 逐项列出引用来源；
2. 明确区分事实、判断和未验证内容；
3. 数字与单位可复核；
4. 输出可保存为独立文件；
5. 结束前列出仍需人工核验的 3 点。
先复述你理解的任务，再开始。

08｜专题一：写作和内容分发的可复用流程

实际问题： 想用 AI 写一篇知识型公众号长文，后续分发到 Threads、X 等平台，但不能让“看起来很像 AI 写的”。

做法： 用原始事实与个人经历做素材；让模型先提文章主线，不要一次写到底；人工补充人物、时间、具体动作与证据；形成一篇可编辑 Markdown；再拆成不同平台的不同长度版本。

验收： 来源必须可点击、核心事实不变、不同平台文案不能捏造用户反馈，文章有读者能执行的下一步。把风格模版与修改记录保留在 Git 仓库或自己管理的文件夹。

Andy 实际工作方法： 我更偏好从具体经历或解决问题入手，而不是把热词堆在标题里。开源教程先交付能运行的资料、步骤和模板，再把长文内容分发。这是方法记录，不承诺某条内容能涨多少粉或成交多少单。

09｜专题二：表格分析，最容易发生“看上去合理”的错误

提示词应要求模型明确：字段定义、时间范围、单位、缺失值处理、公式和引用位置。对于百分比、增长率、占比，要分清“比例的数值”和表格内部百分比格式。CSV 需要实际保存，然后在 Excel/WPS 打开检验乱码与分隔符。

交付至少包含四样东西：清洗后的表格、公式/口径、异常清单、最终解释。再让另一个工具或人工以相同数据重算关键数值。原仓库提供 WORKFLOWS.md 的公开数据练习与 selection.csv 模板。

10｜专题三：网站和小程序，验收的是可运行能力

简单网页的初级路线：选定一个真实页面问题 → 记录界面和核心交互 → 生成 HTML/CSS/JS 或现有框架源码 → 本地打开 → 移动端测试 → 上传到 GitHub Pages。能给出代码不等于网站已经上线，能打开首页不等于下载、菜单和表单都通过。

开发时让 AI 限定文件修改范围、要求在最终答复中列出变更文件、命令和验证结果。不要把 Token、API Key 复制进浏览器端 JS；任何私有凭据只放服务端安全配置。

11｜专题四：AI 产品演示视频，把真实感留给真实操作

Andy 的项目实践： 我在探索用 Gemini 网页版做演示画面、借助 Codex 或工作台生成分镜和可录制页面，并用 Andy Video Skill 等工程方法组织素材。真实的产品 UI 录制、连贯的操作步骤、证据画面和后期节奏，是商业宣传视频可信度的重要来源。

建议流程：一页需求卡 → 5–8 个分镜 → 真实页面连续操作录制 → 核对字幕与事实 → 简洁旁白 → 成片验证。AI 可以辅助组织，但视频不得把未实现功能伪装成真实产品操作，也不能无授权地使用客户品牌素材。

公开项目延伸：Andy Video Skill；这是作者的相关工具仓库，不代表本教程已经对其全部效果做过同题性能测评。

12｜专题五：把 AI 工作流变成可交付的小项目

以“修车阿江”为例，这是作者正在推进的真实本地业务内容项目；可公开表述的工作是围绕修车经验整理故障知识、人物经历与短视频栏目，而不是声称模型帮助门店获得了某个不存在的收入增长。

可以把一次真实采访变成：带时间码的原始摘录 → 一条技术解释脚本 → 三个短标题 → 发布与复盘台账。关键证据仍来自专业人员审校。适合做“同任务多模型比较”，并计算节省的编辑时间，但只有实际记录过前后耗时，才可发布效果数据。

类似地，企业 AI 获客可以从线索资料清洗、一页服务说明、内容分发清单开始，不要用 AI 生成虚构客户评价或假案例。

13｜关联开源工具：不是越多越好

项目 适用场景 需要另行核对
FreeRedact 发布截图前检查脱敏需求 实际处理范围、敏感信息残留
FreeCover 内容封面制作 生成效果、版权、尺寸
FreePhoto 图像处理工作流 本地/云端执行及导出能力
Andy Video Skill 视频制作工作方法 运行条件、素材授权
DNASkill AI 长期记忆与项目上下文 私有数据是否被公开提交
FreeDocs 文档、协作与迁移相关探索 当前 README、功能与依赖

以上仓库可在 GitHub 打开，但不在这里虚构功能已全部验收、成本或社区采用量。统一原则是：先看原仓库 README 与许可证，再看它是否能解决你现在的一个问题。

14｜第三方可选开源栈与许可证边界

Cherry Studio：多模型桌面入口；AnythingLLM：文档与知识工作空间；LibreChat：可自托管会话入口；Ollama：本地运行模型；Dify：工作流编排；Open WebUI：自托管网页入口。

客户端的开源许可、服务端商业条款、模型权重许可证、付费 API 是四套可能不同的约束。Dify 与 Open WebUI 等项目还需要注意对应版本的附加条款。读者应打开各自官方仓库的 LICENSE，而不是一律当作 MIT。

详细入口与核对说明在原项目 OPEN-SOURCE.md。这里没有执行所有工具的安装与国内联网实测，也没有给出“性能排名”。

15｜不丢掉 Claude 的长处：跨工具复用 8 类工作资产

从 Claude 或 Claude Code 迁出不意味着放弃它值得学习的工作方法。要迁的是问题定义、项目上下文、Skills、MCP 权限说明、Agent 交接卡、测试与质量门禁、可编辑成品、恢复记录，而不只是把聊天窗口换成另一个窗口。

例如同一个网站任务：沿用原来的需求、源码和移动端验收标准；Claude Code 用 CLAUDE.md，Codex 可以用 AGENTS.md，Gemini CLI 可以用 GEMINI.md。但各工具的加载范围、执行权限、Hooks 和对外连接不同，须实际确认行为而非认为文件名替换就等价。

使用 Claude 专项迁移教程 保全资产；用 能力移植指南 提炼规则；用 可复制的工作流卡 固定结果。建议从一个公开项目开始实验，避免把客户资料和密钥传入不适当的模型环境。

16｜成本公式：低价不是唯一目标

一个任务真实成本 = 模型订阅分摊 + API/素材/托管费用 + 人工审校/返工时间 × 工时成本 + 合规与运维成本。

例如工具 A 每次生成便宜，但总要重写两遍；工具 B 付费稍高，却能得到可编辑成品。没有记录工时就不能得出哪一个成本更低。用 templates/task-evaluation.csv 记真实结果，至少跑三次不同输入；实验样本少时不要得出普遍性结论。

对于准备做副业的人，先售卖一个清晰可交付的服务，而不是售卖“我会用 AI”。先定义客户输入、具体交付、修改次数、价格和验收，再决定什么工具最划算。

17｜七天起步：能复用，比炫技更值钱

Day 1： 选一项困扰你很久的真实任务，写需求卡。
Day 2： 找到有授权的原料，列出事实来源。
Day 3： 用一个可用工具做第一版，保存独立文件。
Day 4： 人工验收，记录返工与问题。
Day 5： 换一个候选工具，用同一份原料重做。
Day 6： 比较真实成本、可编辑性与恢复难度。
Day 7： 把步骤写成下一次能直接复用的工作流，才考虑自动化。

18｜一个合格的成果包应该长什么样

my-ai-task/
├── input/source.md           # 来源与许可
├── input/brief.md            # 目标和验收
├── output/final.md           # 主要成品
├── output/attachments/       # 真实导出的附件
├── evidence/fact-check.md    # 人工核查记录
└── report.csv                # 耗时、费用、版本与结果

如果要交给客户，附上可编辑版本和一段“你今后怎么更新”的说明。一次演示做好不代表整个工作流稳定；工作流稳定不代表业务一定赚钱。
